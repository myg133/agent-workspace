Agent Workspace
组织方案设计

基于 Git Worktree 的多 Agent 协作开发管理规范
v1.0 2026-08-18 方案设计

1 背景与目标

我们面临的问题

上下文污染
单 Agent 模式下，不同任务互相干扰
上下文压缩时丢失关键信息，结果不达预期
目录混乱
多个开发任务在同一目录并行
文件冲突、耦合严重，难以管理
状态管理缺失
Agent 输出没有统一持久化机制
重启后状态丢失，无法恢复
角色边界模糊
BA、Dev、QA、Deploy 职责混在一起
流程不可控，质量无法保证

设计目标

目录隔离
每个需求独立 worktree
Git worktree 物理隔离
上下文隔离
子 Agent 独立上下文
消除 context 污染
状态持久化
Git 仓库 = 唯一状态源
无状态 Runtime
流程可控
分角色验证门禁
Pre + Post merge

2 整体架构

系统分层

用户交互层
Web 界面 / CLI / API
↓
平台管理层
项目管理 · 需求管理 · 容器编排 · NFS
↓
Agent Runtime 层
Docker 容器 · codewhale · Agent
↓
持久化层
Git 仓库 · NFS 共享存储

三大核心原则

原则 1
一个需求 = 一个容器
容器生命周期 = 需求完整生命周期
原则 2
一个 Runtime = 子 Agent 池
主 Agent 通过 agent 工具创建子 Agent，同进程零开销
原则 3
Git 即状态
启动 git pull 恢复，关闭前 git push 持久化

3 Workspace 目录管理

目录平面

project-root/
├── .git/                          # 中央仓库
├── BA/                            # [demand] 需求管理
├── code/                          # [develop] CI 只读
├── feature-REQ-001/               # [feature/REQ-001] 开发
├── Deploy/                        # [deploy] 部署配置
└── hotfix-JIRA-123/               # [hotfix/JIRA-123] 紧急修复
目录分支使用者权限
BA/demandBA Agent读写
code/developCI 只读只读
feature-REQ-xxx/feature/REQ-xxxDev Agent读写
Deploy/deployDeploy Agent读写
hotfix-xxx/hotfix/xxxDev Agent读写

Worktree 回收机制

触发条件执行者方式
PR 合并Dev Agent 自清理git worktree remove + 删除分支
需求取消BA Agent 强制清理git worktree remove --force
定期巡检BA Agent 兜底扫描所有 worktree 状态
安全检查：删除前确认分支已合并、无未提交变更、无未推送 commit。

4 Git 分支策略

分支用途写入者基分支
develop主开发，CI 构建合并不直接写—
demand需求管理BA Agent独立分支
feature/REQ-xxx需求开发Dev Agentdevelop
deploy部署配置Deploy Agent独立分支
main生产发布release 合并—
release/vx.y.z预发布管理员develop
hotfix/xxx紧急修复Dev Agentmain

分支关系

develop ← feature/REQ-001   (PR 合并)
develop ← feature/REQ-002   (PR 合并)
develop → release/v1.0.0 → main
                            main → deploy (镜像 tag 信号)
                            deploy 独立演进，不 merge 回 main

命名规范

类型格式示例
需求编号REQ-{三位数字}REQ-001
分支名feature/REQ-{xxx}feature/REQ-001
Commit Message[{区域}] {描述} (关联: {需求ID})[Dev] 实现邮箱登录 (关联: REQ-001)
镜像 Tag{GIT_SHA} 或 {GIT_TAG}a1b2c3d 或 v1.0.0

5 Skill 体系设计

核心设计：主 BA Agent 读取 agent-workspace-v2/SKILL.md，按角色截取对应章节，通过 prompt 注入到子 Agent。不需要额外的 skill 发现机制。

文件结构

.agents/skills/
└── agent-workspace-v2/             # 核心 skill（合并版）
    ├── SKILL.md                    # 完整规范（5 个章节）
    ├── init/                       # 初始化流程
    ├── lifecycle/                  # 回收 + 巡检
    └── templates/                  # 通用模板

SKILL.md 内容映射

章节内容注入目标
第一部分：全局规范目录结构、分支策略、命名规范BA Agent 自身加载
第二部分：BA Agent 工作流需求管理、调度、巡检BA Agent 自身加载
第三部分：Dev Agent 工作流开发、自验证、清理Dev 子 Agent inject
第四部分：QA Agent 工作流Pre-merge + Post-merge 验证QA 子 Agent inject
第五部分：Deploy Agent 工作流部署、回滚、环境管理Deploy 子 Agent inject

上下文隔离机制

主 BA Agent 上下文（一直在累积）
  ┌─────────────────────────────────────────────────┐
  │ 用户讨论需求 → 确认方案 → 调度子 Agent          │
  └─────────────────────────────────────────────────┘

                  ↓ 创建子 Agent

                  子 Agent 上下文（独立，用完回收）
                   ┌──────────────────────────────┐
                   │ 完整 skill 注入 + 独立任务    │
                   │ 执行 → 返回 → 回收            │
                   └──────────────────────────────┘
                   ↑ 不会污染主 Agent

8 无状态 Runtime 与状态管理

核心思想：Git 仓库 = 唯一状态源。容器是无状态的，所有状态通过 Git 持久化。启动时 git pull 恢复，关闭前 git push 保存。
启动时
git pull 恢复
读取需求文档、状态、迭代计划、调度信息
运行时
实时写入 Git
每次变更立即 commit，崩溃不丢失
释放时
git push 持久化
所有状态写入仓库，下次启动恢复

需求状态流转

草稿→ 已评审→ 已就绪→ 进行中→ 待验证→ 已验证→ 已完成
进行中 → 已取消
待验证 → 已退回 → 进行中

9 镜像设计与容器生命周期

Dockerfile
FROM ubuntu:22.04
RUN apt-get install -y git curl openssh-client
COPY codewhale /usr/local/bin/
COPY agent-workspace-v2/ /home/codewhale/.codewhale/skills/
COPY entrypoint.sh /entrypoint.sh
ENTRYPOINT ["/entrypoint.sh"]
entrypoint.sh
case $ACTION in
  init)
    codewhale --skill agent-workspace-v2 \
      "初始化 workspace" ;;
  demand)
    codewhale --interactive \
      --skill agent-workspace-v2 \
      --context "BA/demands/$DEMAND_ID/" ;;
esac
git add . && git commit -m "[Agent] 提交"
git push

容器生命周期

项目初始化
一次性，无状态
启动 init 容器 → 创建分支 + worktree → git push → 释放
需求开发
一个需求 = 一个容器
启动 BA 容器 → 讨论 + 子 Agent 调度 → git push → 释放
关键设计：子 Agent 通过 codewhale 的 agent(action="start") 在同一进程中创建。共享 workspace，独立上下文窗口。不需要新容器，不需要新进程。

10 多项目承载方案

NFS 目录结构

/nfs/
├── projects/
│   ├── project-a/workspace/    # 项目 A
│   ├── project-b/workspace/    # 项目 B
│   └── project-c/workspace/    # 项目 C
│
└── containers/                 # 容器状态映射

多容器并行

平台 Server
├── project-a:
│   ├── 需求 REQ-001 → 容器 abc123 (BA Agent)
│   └── 需求 REQ-002 → 容器 def456 (BA Agent)
├── project-b:
│   └── 需求 REQ-001 → 容器 ghi789 (BA Agent)
└── project-c: (无活跃需求)

每个容器挂载不同 NFS 路径：
  abc123: /nfs/projects/project-a/workspace → /workspace
  def456: /nfs/projects/project-a/workspace → /workspace
  ghi789: /nfs/projects/project-b/workspace → /workspace

同一项目可并行多个需求容器
每个需求的 worktree 不同，Git 分支不同，不会冲突
并发安全：同一项目多容器通过分支隔离避免冲突。每个容器只操作自己的 feature 分支。develop 分支操作需串行化。

11 关键技术决策

决策项选择理由
Agent 架构子 Agent 方案同一 runtime 内独立上下文，零开销
Skill 结构1 核心 + 工作流目录主 Agent 读取后按角色截取注入
Skill 注入Prompt 注入读取 SKILL.md 内容，通过 prompt 传入
目录隔离Git Worktree物理隔离，原生支持
状态管理Git 即状态无状态 Runtime，git pull/push
远程架构Docker 容器每个需求一个容器，用完释放
多项目NFS 按项目隔离不同容器挂载不同路径
验证模式分两层验证Pre-merge + Post-merge
镜像 TagGIT_SHA / GIT_TAG默认 commit SHA
部署分支独立 deploy 分支commit 历史 = 审计日志
环境管理目录 + .env 混合values.yaml 放嵌套，.env 放差异
回滚方式git revert 新部署保持审计历史完整

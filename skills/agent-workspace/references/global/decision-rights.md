# 决策权与升级

BA 变"笨"通常不是模型问题，是**决策权没有写清楚**：什么都像该问 Planner，问了又总能得到回答，于是形成依赖。

这份文档只做一件事：**把"谁拍板"写成默认规则**。

## 1. 默认原则

> **BA 是需求所有者，默认自己拍板。**
> Planner 只定三件事：顺序、跨 BA 边界、不可逆事项。

判断标准：**能靠代码、契约、验收标准回答的，不升级。**

## 2. 决策权矩阵

| 问题类型 | 决定者 | 例子 |
|----------|--------|------|
| 实现细节 | **BA** | 字段名、错误码、重试次数、日志格式、目录结构 |
| 验收标准 | **BA** | AC 怎么写、边界值、测试数据 |
| 需求拆分 | **BA** | 拆几个子任务、内部先后 |
| 单 REQ 技术选型 | **BA**（在约束内） | 用现成库还是手写、是否加缓存 |
| 交互/文案细节 | **BA** | 提示语、空状态、默认值 |
| 优先级 / 排期 | **Planner** | 先做 REQ-003 还是 REQ-007 |
| 跨 BA 契约 | **Planner 拍板，BA 提案** | API 字段破坏性变更、共享 schema |
| 资源冲突 | **Planner** | 两个 BA 改同一模块、抢同一环境 |
| 产品范围 / 预算 | **用户** | 要不要做这个功能、砍不砍 |
| 不可逆 / 对外 | **Planner + 用户** | 数据迁移、公开 API 下线、计费变更 |

一句话：**细节归 BA，顺序归 Planner，范围归用户。**

## 3. 只有四种情况可以升级

1. **跨 BA 冲突**：同一契约 / 模块 / 环境，两个 BA 都要改；
2. **优先级或范围**：需要插队、砍需求、改里程碑；
3. **不可逆或对外**：数据迁移、公开 API、计费、合规；
4. **文档互相矛盾**：roadmap、契约、ADR 之间冲突，BA 无法自洽。

其余情况：**BA 决定 + 写进 decisions.md**，不打断 Planner。

## 4. 提问必须带提案

升级时用 `type: question`，正文必须包含：

```text
proposal:    我打算这么做
alternatives: 备选 A / B（可选）
impact:      影响哪些 REQ / 契约 / 时间
default:     如果 2 小时内没有回复，我按 proposal 执行
deadline:    需要答复的时间
```

**没有 proposal 的问题，Planner 不回答**，只回一句"先给方案"。

## 5. 沉默即同意

- Planner 的 SLA：**2 小时**（或当天结束前）；
- 超时未回复 → BA 按 `default` 执行，并在 decisions.md 记录；
- Planner 事后不同意 → 发 `type: decision` + 写 ADR，BA 再调整；
- **不允许"等 Planner 回复"成为阻塞理由**。

## 6. 决策日志

每个需求一份 `BA/demands/REQ-xxx/decisions.md`：

```markdown
| # | 日期 | 决策 | 理由 | 可逆 | 复核 |
|---|------|------|------|------|------|
| D1 | 10-24 | 字段名用 mfaToken | 与 v2 一致 | 是 | Planner 周检 |
```

- BA 写，随需求提交；
- Planner **周检**，不逐条审批；
- 有异议 → ADR + 消息，不阻断当前开发。

## 7. 反模式

| 反模式 | 应该 |
|--------|------|
| "这个字段叫什么？" | BA 定，写进 decisions.md |
| "要不要拆成两个 REQ？" | BA 定；只有影响排期才找 Planner |
| "这个错误码用 400 还是 422？" | BA 定 |
| "先做哪个？" | Planner |
| "能不能改契约？" | BA 提案，Planner 拍板，消费方 ack |
| 问之前不查 `plan/` 与 `decisions/` | 先查；文档没有再加 |
| 把"等回复"当阻塞 | 用 default 继续 |

## 8. 度量

每周看三个数：

| 指标 | 目标 | 从哪看 |
|------|------|--------|
| 每个 REQ 升级问题数 | < 1 | `stats --json` 的 `questions_per_req` |
| 近 7 天提问数 | 下降趋势 | `questions_last_7d` |
| 问题集中在哪个 REQ | 定位需求质量问题 | `questions_by_req` |
| 因"等 Planner"导致的阻塞 | 0 | 人工观察 |

```bash
aw.py stats --json | jq '{questions_total, questions_last_7d, questions_per_req, questions_by_req}'
```

口径：只统计 bus 上 `type: question` 的消息，按 `ref` 里的 `REQ-xxx` 归组；
分母是当前有认领、在队列、或被提问过的 REQ 数。

高于目标，先改文档和决策权，不要先怪模型。

# 任务预检与开工自检

> **BA 决定“任务多大、怎么拆”；子 Agent 只决定“现在能不能按卡开工”。**

## 1. 两个检查，不要混

| 检查 | 谁做 | 回答的问题 |
|------|------|------------|
| 任务预检 | BA | 这个任务多大？要不要拆？拆成几个切片？预算多少？ |
| 开工自检 | 子 Agent | 任务卡和当前代码还对得上吗？能不能直接开工？ |

BA 不做任务预检，子 Agent 就会用大量读文件和 compaction 替它做。
BA 做完预检，子 Agent 就不要重新做一遍“任务大小评估”。

## 2. BA 的任务预检

在 spawn 之前完成，输出到任务卡。

| 项 | 内容 |
|----|------|
| 切片目标 | 一个可独立验证的行为变化 |
| 预期文件 | 具体路径，不是“相关模块” |
| 预期 diff | 大概行数 / 是否跨层 |
| AC 子集 | 这个切片负责哪几条 AC |
| 依赖 | 依赖哪个切片 / 接口 / 迁移 |
| 验证 | 测试命令 / 手工验证 |
| 预算 | 轮数 / 上下文 / 时间 |
| 停止 | compaction 上限、何时交回 |

### 什么时候必须拆

- 涉及 3 个以上模块；
- 预期改 8 个以上文件；
- 同时涉及 DB + API + UI；
- 需要先做迁移、契约、外部服务；
- AC 超过 3 条且互不相关；
- BA 说不出“改哪些文件、怎么验证”。

出现以上任一情况：

1. 先派 Explore 摸清；
2. 按垂直切片拆；
3. 每个切片一个任务卡；
4. 不要把一个完整功能原样交给一个子 Agent。

### 切片原则

- 垂直切片：一个行为 + 一个验证；
- 可独立 commit / review；
- 尽量少文件；
- 依赖明确；
- 不按“所有 DB / 所有 API / 所有 UI”横切。

## 3. 子 Agent 的开工自检

只做 3–5 件事，控制在几分钟、少量读文件：

1. 读任务卡和 evidence；
2. 看 `git diff <base_sha>..HEAD`，确认关键文件没变；
3. 确认入口还在（文件 / 符号 / 路由 / 测试）；
4. 确认测试命令能执行；
5. 确认允许改的文件范围。

通过 → 开始第一次编辑。
不通过 → 停，返回错误码，不要自己重新拆任务。

### 返回码

| 码 | 含义 | 动作 |
|----|------|------|
| `EVIDENCE_STALE` | evidence 与当前代码不一致 | 交回 BA 补 evidence |
| `TASK_TOO_BIG` | 读文件/预算明显超切片 | 交回 BA 重拆 |
| `MISSING_ENTRY` | 任务卡里的入口不存在 | 交回 BA 核对 |
| `BUDGET_EXCEEDED` | 轮数/上下文/时间到上限 | handoff，交回 BA |

返回时带上：已检查什么、实际发现什么、建议怎么拆。不要静默继续。

## 4. 预算与 compaction

| 项 | 软预算 | 硬停 |
|----|--------|------|
| 子 Agent 轮数 | 20 | 30–40 |
| 上下文 | 6–8 万 | 10 万 |
| 时间 | 30 分钟 | 45–60 分钟 |
| compaction | 0 | 1 次 |
| 首次编辑前读文件 | ≤10 | >20 |

规则：

- 到 50% 预算：回报进度 / 风险；
- 到 80%：写 handoff；
- **第一次 compaction 就停**，不要继续压第二次；
- 第二次 compaction = 任务分解失败，回 BA 重拆。

## 5. 子 Agent 不该做的事

- 重新评估整个功能多大；
- 发现任务太大后自己再 spawn 一串子 Agent；
- 因为“不熟”重扫全仓库；
- 把 BA 的切片重新组合成大任务；
- 不汇报就继续跑。

拆分权在 BA；子 Agent 只有执行可行性判断权和建议权。

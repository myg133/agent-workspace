# 会话与子 Agent 预算（工具无关）

> 会话是成本单位。每多一轮，模型都会重新带上上下文；会话越长，每轮越贵。
> 目标不是"少干活"，而是让每个会话有明确产出、明确退出条件，而不是一直开着。

## 1. 先看三个指标

任何客户端 / 运行时都适用：

| 指标 | 怎么看 | 过载信号 |
|------|--------|----------|
| 每轮 prompt tokens | 输入 + 缓存读 + 缓存写 | 平均 > 10 万 |
| 会话轮数 | 一次会话内的模型请求数 | > 100 轮 |
| 子 Agent 数 | 一个 REQ 派生的子会话 | > 3 个 |

再看两个比值：

```text
输出 / 总 tokens      过低（例如 < 0.5%）通常说明上下文过大
产品代码操作 / 文档操作  文档长期高于产品，说明在做"元工作"而不是交付
```

## 2. 默认预算

超过软预算就先压缩上下文 / 收尾；超过硬预算必须停。

| 项 | 软预算 | 硬预算 |
|----|--------|--------|
| 主会话轮数 | 60 轮 | 100 轮 |
| 主会话活跃时长 | 90 分钟 | 2 小时 |
| 每轮 prompt 上下文 | 8 万 tokens | 10 万 tokens |
| 每个 REQ 的主会话数 | 3 个（探索 / 实现 / 验证） | 5 个 |
| 每个 REQ 的子 Agent 数 | 2 个 | 3 个 |
| 每个子 Agent 轮数 | 20 轮 | 30 轮 |
| 文档 / 规划会话 | 30 轮 | 60 轮 |
| 同一个会话连续失败 | 2 次 | 3 次 |

成本 / 额度预算按项目实际单价设置，不要拍脑袋。先统计过去一个月"每个合并 REQ 的平均成本"，再设 70% 为目标。

## 3. 会话生命周期

### 3.1 一个会话只做一件事

按阶段拆会话，不要一个会话从探索做到上线：

```text
探索会话：只读，产出事实清单 / 风险清单
规划会话：只写计划 / 验收 / 决策
实现会话：只改代码 + 目标测试
验证会话：只读验证，产出 PASS / FAIL
文档会话：只做批量文档同步
```

### 3.2 到阈值就交接

- 到 60 轮或 8 万上下文：先写一页 handoff；
- 到 100 轮或 10 万上下文：关掉，开新会话；
- 不要 resume 一天前、跑了几百轮的会话；
- 会话结束前必须留下：目标、当前状态、改动、未完成项、下一步。

### 3.3 不要"开着等"

- 没有明确下一步就退出；
- 不要轮询、不要等待子 Agent 完成后再开一轮"看看"；
- 子 Agent 的结果由父会话在下一轮统一消费。

## 4. 会话任务卡

每次开新会话（或 spawn 子 Agent）先填这张卡：

```text
REQ / 任务：
阶段：探索 / 规划 / 实现 / 验证 / 文档
目标（可验收）：
允许读：
允许写：
预算：最大轮数 ___；上下文 ___；子 Agent ___；成本/额度 ___
模型策略：探索 ___；实现 ___；验证 ___
退出条件：diff / 报告 / 决策 / 阻塞
交接：文件 / commit / 下一会话
不做什么：
```

模板见 `assets/templates/session-card.md.tpl`。

## 5. 子 Agent 门槛

只有以下情况才 spawn：

1. 任务可独立并行，且不会改同一批文件；
2. 需要独立验证（高风险 / 安全 / 资损 / 权限）；
3. 需要上下文隔离（大仓库、不同技术栈、避免污染）。

以下情况**不要** spawn：

- 写 status、更新文档、发消息；
- 简单查找、单文件修改；
- 串行流程（BA → Dev → QA 本身不是并行理由）；
- "多几双眼睛"但没有明确独立范围；
- 父会话自己能在 10 轮内完成的事。

规则：

- 每个 REQ 最多 2–3 个子 Agent；
- 每个子 Agent 必须有明确产物：diff、报告或决策；
- **没有 diff 预期的任务，不 spawn 子 Agent**；
- briefing 只给精确文件清单，不给"自己去看全仓库"；
- 一个主题只开一个 Scout，多个文档合并给一个 Doc Agent；
- 子 Agent 失败不盲目重试超过 2 次。

## 6. 模型路由

按任务难度路由，不按角色名字路由：

| 任务 | 模型档位 |
|------|----------|
| 仓库扫描、文档摘要、status、日志分析 | 低成本 / 快速模型 |
| 普通功能实现、测试补充 | 中等模型 |
| 架构、疑难 bug、安全、关键 review | 强模型 |
| 批量格式化、机械迁移 | 低成本模型 |

原则：

- 不要用强模型在 10 万+ 上下文里做例行阅读；
- 不要让强模型承担文档 / 状态 / 路由工作；
- 强模型只用在"错了代价高"的决策点；
- 换模型后要看质量，不要在关键路径上单纯为省钱降级。

## 7. 上下文卫生

- 只读任务卡列出的文件；需要额外文件先说明理由；
- 用搜索定位，不 `cat` 整个仓库 / 整个大文件；
- 工具输出只保留摘要和关键片段，不把全量日志塞回上下文；
- 长报告写文件 / 链接，不在对话里贴全文；
- 同一个文件不要反复全量读；需要时读 diff 或指定行；
- 到 8 万上下文先压缩 / 交接，不要等到 30 万；
- 一个会话只围绕一个主题，避免多任务交叉污染。

## 8. 什么时候停

满足任一条件就停，不要"再试一次"：

- 目标产物已经出现（diff / 报告 / 决策）；
- 到达预算上限；
- 连续 2 次同样的失败；
- 连续 3 轮没有新增信息；
- 需要人决策 / 外部依赖；
- 子 Agent 返回空结果或只有分析、没有可执行产物。

停下时输出：

```text
目标：
已完成：
未完成：
阻塞：
下一步 / 交接：
```

## 9. 度量

按 REQ 记录，不要只看总 token：

| 字段 | 用途 |
|------|------|
| 会话数 / 请求数 | 判断是否拆得太碎或太长 |
| prompt / output tokens | 判断上下文是否过重 |
| 成本 / 额度 | 算每个合并 REQ 的成本 |
| 子 Agent 数 | 判断协调成本 |
| 产品代码操作 / 文档操作 | 判断是否在做元工作 |
| 合并 REQ 数 / 返工次数 | 算真实产出 |

建议跟踪：

- 每个合并 REQ 的成本；
- 每轮平均 prompt tokens；
- 输出 / 总 tokens；
- 子 Agent / REQ；
- 产品代码操作 / 文档操作；
- 返工率。

目标示例（按项目调整）：

- 每轮 prompt < 10 万；
- 主会话 < 100 轮；
- 每个 REQ 子 Agent ≤ 3；
- 产品代码操作不少于文档操作；
- 每个合并 REQ 成本逐月下降，返工率不上升。

## 10. 反模式

- 一个会话跑 24 小时以上、几百上千轮；
- 每轮 prompt 30 万+，靠缓存硬撑；
- 一个 REQ 开 10+ 个子 Agent；
- 文档 / 规划会话成本与开发会话相当，甚至更高；
- 用最强模型做探索、读文档、改 status；
- 为了"并行"把串行任务拆成多个 Agent；
- 父会话反复轮询子 Agent；
- 没有 diff 的会话继续加轮次"再想想"；
- 把全量日志 / 整个仓库读进上下文；
- 只看总 token，不看每个合并 REQ 的成本。

## 11. 落地

1. 在 `AGENTS.md` 写默认预算；
2. BA / Planner 派单时附会话任务卡；
3. 每个 REQ 记录会话数、子 Agent 数、成本；
4. 每周复盘一次：最贵的会话产出了什么；
5. 先砍"无 diff 会话"和"文档长会话"，再谈模型降级。

> 预算不是限制能力，是防止把 token 花在上下文重建和协调上。

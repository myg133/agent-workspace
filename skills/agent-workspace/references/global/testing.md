# 测试克制：按风险测，不按覆盖率测

> 测试是投资，不是交付物。每条测试都会持续消耗执行时间、维护成本和 agent token。
> 目标不是"测得多"，而是"用最少的测试抓住最可能坏的行为"。
>
> 测试只是成本的一部分；会话轮数、上下文和子 Agent 预算见
> [session-budget.md](session-budget.md)。

## 1. 先问三个问题

1. 这次改动最可能坏什么？
2. 现有测试里哪条能覆盖？能复用吗？
3. 如果没有，最便宜的验证是什么？

答不出第 1 条，就不要写这条测试。

## 2. 预算（默认值）

项目可以在 `AGENTS.md` 或测试策略里调整，但必须显式写出来。

| 项 | 默认预算 |
|----|----------|
| 每个任务新增测试 | **≤ 3 条** |
| Bug 修复 | **1 条回归测试**（修之前失败，修之后通过） |
| 重构 | **0 条新测试**，只跑现有测试 |
| 单测运行时间 | **< 100ms / 条** |
| 集成测试 | **< 5s / 条**，标记 `integration` |
| fast lane | **< 60s** |
| related lane | **< 3min** |
| full suite | 只允许 CI / merge 前跑；agent 默认不跑 |
| 单条测试 setup | **> 20 行** 或 **> 3 个 mock** → 升级测试层级或放弃 |

超过预算不是绝对不能做，但必须说明"这条测试防止什么高风险回归"，并由人确认。

### 2.1 测试计划（写测试前先填）

```text
风险：这次改动最可能坏什么？
现有覆盖：哪个现有测试能覆盖？能复用吗？
新增：最多 3 条，每条写“能抓住的 bug”
不测：哪些场景暂不测，为什么
执行：fast / related，预计耗时
```

超过 3 条，先问人；答不出风险，就不写。

## 3. 选最便宜的层

| 要验证的东西 | 优先用 | 不要 |
|--------------|--------|------|
| 纯函数、校验、状态转换 | 单测 | 起数据库 / HTTP / 浏览器 |
| 模块边界、文件、DB、HTTP | 集成测试（标记 `integration`） | 为每个分支写 E2E |
| 关键用户链路 | 少量 E2E，merge/nightly 跑 | 用 E2E 覆盖所有边界 |
| 外部服务契约 | 契约测试 / mock 边界 | 真连第三方做全链路 |
| 配置、文档、样式、日志 | 静态检查 / 人工 | 断言文案和格式 |
| 不确定值不值得测 | 先记录"未验证" | 为了安心补一堆测试 |

**TDD 可选，不是硬性要求。** 核心算法、并发、资损、权限、Bug 回归适合先写测试；
CRUD、配置、UI 布局、一次性脚本不强制。

## 4. 什么不测

- 第三方库 / 框架 / 语言运行时自己的行为；
- 私有方法、内部数据结构、实现细节；
- 日志文案、错误提示格式、CLI help 文本；
- 生成代码、自动迁移脚本、纯 getter/setter；
- 本次没有改动的代码；
- 同一个行为在多个层重复测；
- 为了覆盖率数字而存在的"占位测试"。

## 5. 停止条件

满足以下条件就停，不要继续补测试：

- 本次改动的目标测试通过；
- related 测试通过；
- lint / 类型检查通过；
- 没有未解释的失败。

其他规则：

- **full suite 只在 merge 前 / CI 跑一次**，不要每改一行跑全量；
- 与本次 diff 无关的失败：记录为 `pre-existing`，不修、不阻塞；
- 同一失败修 **2 次**仍不成就回滚测试、标 `TODO`，继续做功能；
- 测试需要 `sleep`、重试才稳定：标记 flaky 并隔离，不要靠加大超时"修好"；
- 目标测试通过后，不再为了覆盖率补测试。

## 6. 失败分诊

按顺序判断：

1. 是不是本次 diff 引起的？
2. 测试是不是断言了实现细节？
3. 是不是环境 / flaky / 测试数据问题？
4. 是产品 bug，还是测试写错？

处理原则：

- 产品 bug：修产品，保留测试；
- 测试写错：修测试，不要为了通过而放宽断言；
- 无关失败：记录后跳过，交给对应模块负责人；
- 修不动：先回滚测试，保留功能代码和 `TODO`，不要卡住主任务。

## 7. 三档执行

建议项目提供统一入口：

```bash
./scripts/test fast      # 本次改动的单测，目标 < 60s
./scripts/test related   # 受影响模块的集成测试，目标 < 3min
./scripts/test full      # 全量；只允许 CI / merge 前 / 人明确要求
```

示例（按项目技术栈替换）：

```bash
# Python
pytest -q --tb=short --maxfail=1 tests/unit -k "changed_area"

# JS / TS
vitest related --run
# 或
jest --findRelatedTests <changed-files>

# Go
go test ./pkg/changed/...
```

输出纪律：

- 用 `-q` / `--tb=short` / `--maxfail=1`，不要一次打印几千行；
- 只读失败摘要和相关堆栈，不要 `cat` 整个日志；
- 全量测试最多跑一次；CI 负责最终门禁；
- 不要把测试输出原样贴进上下文。

## 8. 分工

| 角色 | 测试职责 |
|------|----------|
| **Dev** | 实现 + 1–3 条目标/回归测试；跑 fast / related；不默认跑 full |
| **QA** | 从需求设计风险用例；跑 related / full；审查测试有效性；不替 Dev 补测试 |
| **CI** | 跑 full + E2E；给出摘要，不要求 agent 读全量日志 |
| **BA** | 在 acceptance 里写清风险、验证层级、是否自动化；不追求覆盖率 |

测试用例只覆盖**风险最高的 AC**：每个 AC 最多 1 条主路径 + 必要边界。
低风险 AC 可以标"手工验证 / 暂不自动化"，并写清理由。

## 9. 测试套件减肥

如果 full suite 超过 5–10 分钟，先治理套件，再谈"多测"：

- 按耗时排序，找出最慢的 10 个测试；
- 把依赖 DB / 网络 / 文件系统 / 浏览器的测试标记 `integration`，移出 fast lane；
- 用 session 级 fixture 复用临时仓库、容器、服务；
- 合并重复测试：一个行为只在一个层测；
- 删除断言实现细节、日志文案、私有方法的测试；
- 全量测试加并行（在隔离允许的前提下）；
- flaky 测试隔离到单独 job，不要阻塞主流水线。

目标：**fast lane 60 秒内跑完**，agent 才愿意经常跑；full 放 CI，不占 agent 上下文。

## 10. 度量

不要只看总覆盖率，建议跟踪：

- fast / related / full 三档耗时；
- 每个任务新增测试行 / 新增生产代码行；
- 测试相关 token 占比；
- flaky 测试比例；
- 需求交付周期；
- 逃逸缺陷（合并后才发现的问题）。

如果要覆盖率，用**变更行覆盖**（diff coverage），不要用全仓库总覆盖率做 agent 目标。
建议从 70–80% 变更行覆盖起步，按项目风险调整。

## 11. 给 agent 的硬约束（可直接粘贴）

```text
## 测试预算
- 默认只跑 fast / related；禁止默认跑 full。
- 每个任务最多新增 3 个测试；bugfix 只加 1 个回归测试；重构不新增。
- 单测 <100ms；需要 >20 行 setup 或 >3 个 mock 时，升级为集成测试或放弃。
- 不测试未改动代码、第三方库、私有实现、日志/文案/格式、生成代码。
- 先给测试计划（风险 / 现有覆盖 / 新增 / 不测 / 预计耗时）；超过 3 条先问人。
- 目标测试 + related 通过即停止；不要为了覆盖率补测试。
- 全量失败若与本次 diff 无关：记录为 pre-existing，不修。
- 同一失败修 2 次不成：回滚测试，标 TODO，继续。
- 测试输出只读摘要；不要贴全量日志。
```

## 12. 评审测试时只问五个问题

1. 这条测试防止什么回归？
2. 修之前它会失败吗？
3. 它测的是行为还是实现细节？
4. 能否用现有测试或更低层替代？
5. 它跑多久、维护成本多大？

答不上来，就删掉或改成更小的验证。

你的 agent 时间
主要花在哪？

不要想“应该”，想最近一周真实发生的。

现场点击累加，不联网。

结果通常不是“某一项最高”，而是“几项叠加”：探索、协调、上下文，互相喂养。

现象 · 真实审计

功能没做多少，
token 没少耗

长会话

62 小时 / 1,544 轮

会话没有退出条件，每轮都背完整历史。

大上下文

30–44 万 prompt / 轮

不是模型贵，是每轮带的东西太多。

低产出

45% 花在文档 / 规划

产品代码操作远少于状态、报告和探索。

最贵的不是一次回答，是每一轮都重新带上的上下文。
拆账 · 公式

先把账单拆开

总成本 ≈ 请求数 × 每轮上下文 × 单价
        + 输出成本
        + 缓存偏差

输出 token 通常最少；真正的大头是每轮都重新发送的上下文。

请求数

轮数 × 子 Agent 数
任务越大，轮数越多。

每轮上下文

历史 + 工具输出 + 角色规范
会话越长，越接近线性增长。

单价

模型 × 缓存命中
缓存降单价，不降上下文长度。

杠杆 · 顺序

五个杠杆，
按 ROI 排序

01 最优先

减少轮数

任务预检、垂直切片、一次 compaction 就停。

02 最优先

减少每轮上下文

工作集、evidence、handoff；不要把全仓库塞进去。

03 其次

提高缓存命中

稳定前缀、少改 base、任务卡追加在后面。

04 再次

降低单价

探索/文档用低成本模型；强模型只留给关键决策。

05 最后

减少返工

evidence、handoff、验收前置；返工是双倍上下文。

顺序错了

先换便宜模型，往往只是把错误答案跑得更快。

思维工具 · 四问

开一个会话前，
先问四句

01 必要性

这件事必须做吗？

不做会怎样？能不能缩小范围？

02 时机

必须现在做吗？

能不能等接口稳定、依赖合入？

03 主体

必须由这个会话做吗？

能不能换短会话、子 Agent、脚本？

04 上下文

必须带这么多上下文吗？

哪些是稳定事实，哪些是任务状态，哪些可以外置？

四个“必须”里，只要有一个是否，成本结构就会变。

上下文 · 心智模型

上下文不是记忆，
是工作台

稳定事实

项目地图

架构、命令、约定、坑。放 base / 文档，按需引用。

任务状态

当前切片

目标、AC、evidence、待验证项。放任务卡 / handoff。

工具输出

临时材料

只留摘要和 path:line；不要把全量日志塞回上下文。

工作台只放“现在要动手”的东西；仓库和历史留在磁盘上。
上下文 · 污染

四种上下文污染

01 过期

旧文件内容

base 里是旧版本；每轮都在读死代码。
修复：base_sha + diff 校验。

02 偏见

旧结论

探索时的错误假设，被后续所有轮继承。
修复：evidence 标“已确认 / 待验证”。

03 串味

兄弟任务细节

功能会话把任务 1 的讨论带进任务 2。
修复：共同 checkpoint 一次性 fork。

04 噪音

全量工具日志

真正有用的只有几行，其余都是背景。
修复：摘要 + path:line。

污染的代价不是“多几行”，是模型把注意力花在错误的东西上。

会话 · 租约

agent_id 是工位
session 是租约

状态按什么隔离换 session 后
inbox / 已读agent_id保留
claim / WIPagent_id保留
session 文件 / mapsession_id新会话覆盖
wake / 通知agent_id + session需要清 notified / 重定路由
换班：旧会话 handoff → 停进程；新会话同一 agent_id → whoami → resume。
会话 · 时机

什么时候该换会话

01 预算到

轮数 / 上下文到阈值

先 handoff，再开新会话。

02 compaction

第一次压缩

停止扩张，交回 BA 重拆或换人。

03 阶段切换

探索 → 实现 → 验证

一个阶段一个会话，不要一路做到底。

04 任务完成

产出已交

立即退出；不要“挂着等消息”。

换会话不是重启，是交接；交接质量决定新会话的成本。
任务 · 分片

BA 做预检
子 Agent 只做开工自检

BA 任务预检
  • 模块 / 文件 / AC / 依赖 / 预期 diff
  • 说不出“改哪些文件、怎么验证” → 先探索
  • 跨 3+ 模块、8+ 文件、DB+API+UI → 拆
  • 每个切片一个任务卡，一个验证点
子 Agent 开工自检
  • evidence 对 HEAD、入口存在、测试命令可执行
  • 不重做任务大小评估
  • 失败返回 EVIDENCE_STALE / TASK_TOO_BIG
  • 第一次 compaction 就停，交回 BA
多次 compaction 不是任务难，是任务没拆。
任务 · 探索权

一个任务，
一个探索 owner

BA

业务 / 验收 / 文档

不深读实现，不画完整调用链；需要实现理解就交给 Dev/Explore。

Explore / Dev

代码探索唯一 owner

产出 path:line、命令、假设、待验证；下一个人消费 evidence，不重新发现。

Evidence 最小字段

base_sha · confirmed · commands · unknowns · files_read · do_not_reread

没有 fork 时，evidence 是必须的；有 fork 时，也不要让子会话重新探索。

框架 · 四层

成本不是一个点，
是四层结构

L1 任务

做不做 / 多大

切片、验收、依赖。
指标：轮数、返工。

L2 会话

多长 / 多重

生命周期、上下文水位、handoff。
指标：prompt / 轮。

L3 请求

带什么 / 命中谁

工作集、模型、缓存。
指标：cache hit、单价。

L4 系统

怎么路由 / 怎么观测

模型路由、账本、门禁。
指标：每 REQ 成本。

先改 L1/L2，再改 L3/L4；顺序反了，容易优化一个不存在的瓶颈。

度量 · 账本

每个 REQ 记六个数

字段用途
会话数 / 轮数判断拆得太碎还是太长
prompt / 轮判断上下文是否过重
output / total过低通常是上下文过大
子 Agent 数判断协调成本
产品操作 / 文档操作判断是否在做元工作
合并 REQ / 返工算真实产出，而不是忙碌感
不要只问“花了多少”，要问“每个合并功能花了多少”。

收束 · 三句话

带走三句话

01

成本是结构，不是单价

先砍轮数和上下文，再谈模型和缓存。

02

上下文是工作台，不是仓库

附录 A · 锚点

Prompt Cache：
省单价，不省上下文

  • 稳定前缀 + 追加任务卡 → 更容易命中
  • cache write 有成本；cache read 通常更便宜
  • TTL 过期、前缀变化、模型切换 → miss
  • 命中率提高，仍要发送完整上下文

后续可展开：缓存 key 怎么算？多长 TTL？命中率怎么测？

一句话

缓存优化的是“重复前缀的单价”，不是“每轮带多少东西”。

附录 B · 锚点

KV Cache：
为什么长上下文更贵

Prefill

先把上下文算一遍

计算量大，决定首 token 延迟；上下文越长，prefill 越久。

Decode

每 token 读 KV

显存带宽是瓶颈；长上下文 + 大 batch 更吃显存。

后续可展开：KV cache 内存怎么估？PagedAttention？batch 与延迟的权衡？

附录 C · 锚点

会话树：
fork 什么，不 fork 什么

project
├── feature A
│   ├── task 1
│   └── task 2
└── feature B
    ├── task 3
    └── task 4
边界
  • 对话树 ≠ 所有权树
  • base 压缩到 20–30k 再 fork
  • 每个任务独立 agent_id / claim / worktree
  • fork 不自动合并结果

实验状态：先跑 2 个任务，验证身份、claim、worktree 不串。

立意

单 Agent 是工具
多 Agent 是组织

  • 工具解决"能不能做"——能力、上下文、提示词
  • 组织解决"一起做"——分工、契约、账本
  • 组织需要制度——制度必须可执行，否则只是愿望
AI-Native 不是把 AI 塞进旧流程，
而是让流程长成 AI 能跑的样子。

诊断

三个病根

01

协调没有载体

谁在做什么只存在于对话上下文里。上下文一换、会话一重启，事实就消失了。

02

流程没有门禁

"先读消息再认领""合并前检查契约"——写成文档就是建议，不写进工具就等于没有。

03

事实没有版本

接口约定散落在聊天记录里，改没改、谁确认的、影响谁，全都不可追溯。

所以 agent-workspace 的目标不是"让 Agent 更强"，
而是把协调变成 Git 里可审计的事实。

核心思想

四个"即"

STATE

Git 即状态

需求状态、认领、消息、契约，全部落在 git 对象上。容器可以丢，仓库不会。

ISOLATION

目录即隔离

一个需求一个 worktree。上下文隔离靠目录，不靠"请勿修改其他文件"。

CONTRACT

契约即版本

接口是带版本的文件，消费方 pin 版本，变更要回执。不靠口头对齐。

GATE

门禁即代码

规则写进工具：不读消息不能认领，pin 落后不能合并。文档负责解释，代码负责执行。

前置条件

开始之前：你需要的不是平台

硬前提（缺一个就跑不起来）

  • 一个带远端的 git 仓库——GitHub / GitLab / 自建均可
  • 主分支 push 权限——认领与 bus 都靠 push 仲裁
  • Agent 能执行 shell 与 git——Claude Code / omp / Codex 都行
  • Python 3.8+ 与 git 2.20+——aw.py 只用标准库
  • 至少 2 个并行会话——我们当前跑 8 个

可选（决定你能走多远）

  • CI：从 develop 构建、跑测试、产出镜像
  • CD：消费 deploy 分支（ArgoCD / Helm / Kustomize）
  • staging 环境：Post-merge 验证需要真实运行时
  • 制品仓库：ACR / Harbor / ECR
没有 CI/CD 也能用结构 + 协作 + 认领；
但 QA 的 Post-merge 与 Deploy 阶段会退化成"人工检查"。

分支模型 · 二

每条分支的职责边界

分支类型归属谁写合并方向关键约束
workspaceorphan<repo-root>BA（极少）不与任何分支合并只跟踪 README + .gitignore；禁止 PR
mainorphan无 worktree发布管理员只从 release 合入只打 tag；不直接提交
develop普通code/仅 PR 合并→ releaseCI 构建源；不直推
demandorphanBA/BA不合并需求/契约/ADR 的唯一真相
deployorphanDeploy/Deploy / CD不合并只放部署配置；不做构建
busorphan无 worktree所有 BA不合并零文件；禁 force-push；禁 checkout
feature/REQ-xxx普通feature-REQ-xxx/Dev→ develop（PR）一需求一分支；合并即回收
release/vX.Y.Z普通无（临时）发布管理员→ main + tag只修 bug；不加功能
hotfix/xxx普通hotfix-xxx/Dev→ main + 回合 develop从 main 切出；漏回合就会复发

原则：一个事实，一个写者；一条分支，一个归属目录。没有归属目录的分支（main / bus / release）都不接受手工 checkout。

状态模型

哪些是真身，哪些只是缓存

状态位置是否同步丢了会怎样
worktree / 未提交代码本机磁盘否重新 clone 可恢复；未提交的改动丢失
.aw/claims 认领本机否需重新认领；跨机会出现"两个人以为自己是 owner"
.aw/msg-read 已读本机否重读一遍（重复，但不丢）
.aw/outbox 待发消息本机否未推送的消息丢失
bus 消息远端分支是fetch 即可恢复
demand 需求 / 契约远端分支是fetch 即可恢复
develop / main / release远端分支是代码的唯一真相
镜像 / 集群状态CI / CD外部由 git 重新渲染，不能手工改
同步点 pull --rebase msg flush fetch origin bus push feature
远端是真相，本机是缓存 + 协调层。跨机时 .aw 不可见，认领只能退回 git 语义。

阶段一 · 结构

一个被迫的设计：workspace 根分支

起点：knodo 的分支模型

  • 01knodo 里分支是平铺的，没有"根分支"这个概念
  • 02但 git 仓库根必须 checkout 一个分支——它得有归属
  • 03若让根承载业务代码，worktree 只能嵌套，越用越深
  • 04于是引入 orphan workspace：只放 README + .gitignore
  • 05代价：worktree 必须平铺；收益：根永远干净，平台目录 = 仓库根

为什么不用 main 当根？根会被业务代码占满，worktree 只能嵌套。 

# workspace 分支的 .gitignore
*
!*/
!.gitignore
!README.md
/*/          # 屏蔽所有一层子目录

# 效果
$ git ls-files
.gitignore
README.md      # 永远只有这两个
结构不是审美，是把"不该发生的事"变成不可能。
阶段二 · 协作

多 BA：从"约定"到"提交"

  • 两个 BA 同时领同一个需求
  • 状态文件互相覆盖，最后谁改的说不清
  • 会话崩溃后，没人知道它领过什么
  • REQ 编号认领：写进 req-registry.md 再 push
  • Session ID + 懒注册：注册绑定在第一次写操作里
  • git log --grep "session:" 就是审计日志
当时对了什么

用 git 的 push 原子性当锁，零外部依赖。

当时埋了什么

共享一张 Markdown 表 → 4 个进程读改写竞争，必然丢更新。

后来怎么补

v1.3 改成"一任务一文件 + 文件锁 + doctor 修复"。

设计深潜 · 一

把消息做成空提交

  • 零文件 orphan 分支 bus，commit message 就是消息体
  • git commit-tree 直接造 commit：不 checkout、不碰工作区

  • 离线先落 .aw/outbox，恢复后自动补推

设计深潜 · 二

一次真实的"吞消息"

旧：时间游标

游标 = (at, id)
未读 = 消息 > 游标
↓
发送端时钟慢 3 秒
↓
消息 at 早于游标 → 判定已读
↓
静默跳过，永远看不到

新：消息 id 集合

已读 = { id1, id2, ... }
未读 = bus 消息 - 已读
↓
与时钟无关
↓
乱序到达照样能看见
↓
--limit 只标记显示过的
分布式系统里，顺序不能用时间去表达。

修复后补了 3 个回归用例：乱序到达、limit 截断、多 agent 隔离。

决策框架

什么时候才该做平台

  • 多租户 / 跨组织：需要权限、配额、隔离
  • SLA 与可观测性：要保证 99.9%，要指标看板
  • 非技术用户：不能要求他们装 Python、读 SKILL
  • 合规审计强制：需要集中留存与签名

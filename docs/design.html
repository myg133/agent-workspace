背景与目标

问题定义

上下文污染
单 Agent 模式下，不同任务上下文相互干扰
上下文压缩时丢失关键信息，导致结果不达预期
目录混乱
多个开发任务在同一个目录中并行
文件冲突、耦合严重，难以管理
状态管理缺失
Agent 输出没有统一持久化机制
重启后状态丢失，无法恢复
角色边界模糊
BA、Dev、QA、Deploy 职责混在一起
流程不可控，质量无法保证

设计目标

目录隔离
每个需求独立的 worktree
Git worktree 实现物理隔离
上下文隔离
子 Agent 独立上下文窗口
消除 context 污染
状态持久化
Git 仓库 = 唯一状态源
无状态 Runtime，随时恢复
流程可控
分角色分阶段验证门禁
Pre-merge + Post-merge 验证

整体架构

系统分层

用户交互层
Web 界面 / CLI / API
↓
平台管理层
项目管理 | 需求管理 | 容器编排 | NFS 存储
↓
Agent Runtime 层
Docker 容器 · codewhale · BA/Dev/QA/Deploy Agent
↓
持久化层
Git 仓库 · NFS 共享存储

核心架构原则

原则 1
一个需求 = 一个容器
容器生命周期 = 需求完整生命周期
原则 2
一个 Runtime = 子 Agent 池
主 Agent 通过 agent 工具创建子 Agent，同进程无额外开销
原则 3
Git 即状态
启动 git pull 恢复，关闭前 git push 持久化

Worktree 回收机制

触发条件执行者方式
PR 合并到 developDev Agent 自清理git worktree remove + 删除分支
需求取消BA Agent 强制清理git worktree remove --force
定期巡检BA Agent 兜底清理扫描所有 worktree 状态
手动触发用户指定 worktree 清理
安全检查：删除前必须确认分支已合并、无未提交变更、无未推送 commit、需求状态非"进行中"。异常情况不自动删除，标记待处理。

Git 分支策略

分支用途写入者基分支
develop主开发分支，CI 构建合并不直接写—
demand需求管理BA Agent独立分支
feature/REQ-xxx需求开发Dev Agentdevelop
deploy部署配置Deploy Agent / CI独立分支，不与 main 合并
main生产发布标记仅从 release 合并—
release/vx.y.z预发布发布管理员develop
hotfix/xxx紧急修复Dev Agentmain

分支关系

develop ← feature/REQ-001   (PR 合并)
develop ← feature/REQ-002   (PR 合并)
develop → release/v1.0.0 → main
                            main → deploy (镜像 tag 信号)
                            deploy 独立演进，不 merge 回 main

Skill 体系设计

注入方式：主 BA Agent 读取 agent-workspace-v2/SKILL.md，按角色截取对应章节，通过 prompt 参数注入到子 Agent。不需要额外的 skill 发现机制。

上下文隔离机制

主 BA Agent 的上下文（一直在累积）
  ┌─────────────────────────────────────────────────────┐
  │ 用户讨论需求 → 确认方案 → 调度子 Agent              │
  │ 子 Agent 返回结果 → 更新状态 → 继续下一步           │
  └─────────────────────────────────────────────────────┘

                  ↓ 创建子 Agent，独立上下文

                  子 Agent 的上下文（用完回收）
                   ┌──────────────────────────────┐
                   │ 任务描述（完整 skill 注入）    │
                   │ 执行任务                      │
                   │ 返回结果                      │
                   └──────────────────────────────┘
                   ↑ 不会污染主 Agent 的上下文

验证门禁

门禁 1：Pre-merge
QA 验证通过 → 允许合并到 develop
在 feature worktree 中完成：追溯性审查、代码审查、测试验证
门禁 2：Post-merge
QA 验证通过 → 允许部署到 production
在 staging 环境中完成：e2e 测试、回归测试、性能测试

无状态 Runtime 与状态管理

核心思想：Git 仓库 = 唯一状态源。容器是无状态的，所有状态通过 Git 持久化。启动时 git pull 恢复，关闭前 git push 保存。

状态恢复机制

BA Agent 启动时（容器启动）：
────────────────────────────────────────
1. git pull → 获取最新仓库状态
2. 读取 BA/sprint/current.md       → 当前迭代
3. 读取 BA/dispatch/registry.md    → Agent 注册表
4. 读取 BA/decisions/              → 架构决策历史
5. 读取 BA/demands/REQ-xxx/        → 需求描述 + 状态
   → 这些文件就是 BA Agent 的"状态"
   → 不需要恢复对话历史，需求文档已足够

BA Agent 运行时（容器运行中）：
────────────────────────────────────────
1. 所有变更立即写入 Git 仓库
2. 每次 git commit 后，状态已持久化
3. 即使容器崩溃，重新启动后从 Git 恢复

BA Agent 释放时（容器停止）：
────────────────────────────────────────
1. git add + git commit + git push
2. 所有状态已持久化在 Git 仓库中
3. 下次启动时，从 Git 恢复

需求状态流转

草稿→ 已评审→ 已就绪→ 进行中→ 待验证→ 已验证→ 已完成
进行中 → 已取消
待验证 → 已退回 → 进行中

镜像设计与容器生命周期

Dockerfile

FROM ubuntu:22.04

RUN apt-get update && apt-get install -y \
    git curl openssh-client && rm -rf /var/lib/apt/lists/*

COPY codewhale /usr/local/bin/codewhale
COPY agent-workspace-v2/ /home/codewhale/.codewhale/skills/agent-workspace-v2/
COPY ssh-key /home/codewhale/.ssh/id_rsa
COPY entrypoint.sh /entrypoint.sh

ENTRYPOINT ["/entrypoint.sh"]

entrypoint.sh

#!/bin/bash
set -euo pipefail

# 环境变量：PROJECT_GIT_URL, PROJECT_ID, DEMAND_ID, ACTION

if [ ! -d "/workspace/.git" ]; then
    git clone $PROJECT_GIT_URL /workspace
else
    cd /workspace && git pull
fi

cd /workspace

case $ACTION in
    init)
        codewhale --skill agent-workspace-v2 \
            "初始化 workspace，按照 agent-workspace-v2 规范执行"
        ;;
    demand)
        codewhale --interactive \
            --skill agent-workspace-v2 \
            --context "BA/demands/$DEMAND_ID/"
        ;;
esac

git add . && git commit -m "[Agent] 自动提交 - $DEMAND_ID" && git push

容器生命周期

项目创建：
  [平台] 创建项目 → 填入 Git 地址 → 拉取 Git 仓库到 NFS
  [平台] 启动 init 容器 → 挂载 NFS
  [容器] 执行初始化 → 创建分支 + worktree → git push → 释放
         ↑ 一次性，无状态

需求创建：
  [平台] 创建需求 → 创建 feature 分支
  [平台] 启动 BA 容器 → 挂载 NFS
  [容器] git pull → 加载 skill
  [容器] BA Agent 与用户讨论需求
  [容器] 创建子 Agent 开发/验证/部署
  [容器] git push → 释放
         ↑ 一个容器跑完一个需求的完整生命周期
关键设计：子 Agent 通过 codewhale 的 agent(action="start") 在同一进程中创建。共享 workspace，独立上下文窗口。不需要新容器，不需要新进程，零额外开销。

多项目承载方案

NFS 目录结构

/nfs/
├── projects/
│   ├── project-a/workspace/        # 项目 A 的 Git 仓库
│   │   ├── .git/  code/  BA/  Deploy/
│   ├── project-b/workspace/        # 项目 B 的 Git 仓库
│   └── project-c/workspace/        # 项目 C 的 Git 仓库
│
└── containers/                     # 容器状态映射
    ├── project-a-demand-001.json   # 需求 REQ-001 → 容器 abc123
    └── project-b-demand-001.json   # 需求 REQ-001 → 容器 def456

多容器并行

平台 Server
├── project-a:
│   ├── 需求 REQ-001 → 容器 abc123 (BA Agent，活跃中)
│   └── 需求 REQ-002 → 容器 def456 (BA Agent，活跃中)
├── project-b:
│   └── 需求 REQ-001 → 容器 ghi789 (BA Agent，活跃中)
└── project-c: (无活跃需求，无容器)

每个容器挂载不同的 NFS 路径：
  abc123: /nfs/projects/project-a/workspace → /workspace
  def456: /nfs/projects/project-a/workspace → /workspace  ← 同一项目
  ghi789: /nfs/projects/project-b/workspace → /workspace

同一项目可同时运行多个需求容器
因为每个需求的 worktree 不同（feature-REQ-001 vs feature-REQ-002）
Git 分支不同，不会冲突
并发安全：同一项目多个需求容器的 Git 操作通过分支隔离避免冲突。每个容器只操作自己的 feature 分支。如果两个容器都需要操作 develop 分支（如合并 PR），需要串行化——BA Agent 应等待一个需求完成后再处理下一个。

关键技术决策

决策项选择理由
Agent 架构子 Agent 方案同一 runtime 内独立上下文，无需额外容器，零开销
Skill 结构1 核心 + 工作流目录主 Agent 读取后按角色截取注入，避免多文件拼凑
Skill 注入方式Prompt 注入主 Agent 读取 SKILL.md 内容，通过 prompt 参数传入子 Agent
目录隔离Git Worktree物理隔离，原生 Git 支持，无额外依赖
状态管理Git 即状态无状态 Runtime，启动 git pull，关闭前 git push
远程架构Docker 容器每个需求一个容器，挂载 NFS，用完释放
多项目NFS 按项目隔离不同容器挂载不同 NFS 路径，物理隔离
验证模式分两层验证Pre-merge（代码级）+ Post-merge（运行时）
镜像 TagGIT_SHA / GIT_TAG默认 commit SHA，发布用 Git Tag，特殊可用户指定
部署分支独立 deploy 分支不与 main 合并，commit 历史 = 部署审计日志
环境管理目录 + .env 混合values.yaml 放嵌套结构，.env 放环境差异变量
回滚方式git revert 新部署回滚 = 新的部署操作，保持审计历史完整

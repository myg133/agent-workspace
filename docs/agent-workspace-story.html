思维框架 · 三问

先问三个问题，
而不是先选工具

01 空间

他们的工作区隔离了吗？

没有隔离，所有协作都是事故。

02 事实

每份状态有唯一写者吗？

没有唯一写者，信息越多越乱。

03 规则

规则能被执行吗？

写不进工具，等于没有规则。

先物理隔离，再谈协作；先唯一写者，再谈自治。
问题 01 · 空间

两个 Agent，
改同一个目录

现场

Agent A 在改登录，Agent B 在改支付；
它们共享同一个 checkout，互相覆盖。

直觉解法

“让他们小心一点”“改之前先看一眼”。
结果：仍然冲突，只是更晚发现。

现象：文件互相覆盖直觉：加提醒约束：共享目录 = 共享事实
不是模型不听话，是它们共享了同一个“事实源”。
设计 01 · 隔离

一个需求，
一个 worktree

repo/
├── main
└── .worktrees/
    ├── REQ-101/
    └── REQ-102/
01 隔离

每个 REQ 一个工作区，互不覆盖。

02 回收

合并即回收；worktree 是容器，不是永久分支。

worktree 解决了“互相踩”，但制造了新的问题：
这么多工作区，谁是真身？
问题 02 · 拓扑

分支各自为政，
谁是事实？

每个 worktree 都像一条独立分支；合并时才发现，它们没有共同根。

工作区
workspace root容器，不是代码
→
code/产品代码主线
事实
BA/需求、状态、契约
Deploy/发布与回滚
我们把“代码、需求、部署”拆成三条长期分支；
worktree 只是它们的临时视图。
设计：workspace 根 + 三条长期线新问题：谁能写哪条线？
问题 03 · 权限

文档写了“谁能改”，
但工具不知道

角色能写不能写
BABA/ 需求与状态产品代码
Dev自己的 feature worktree别人的 worktree、BA/ 状态
QA验证报告产品代码（只读验证）
DeployDeploy/ 发布线业务代码
规则不写进工具，就只是一句“请大家自觉”。
新问题：Agent 之间怎么说话？
问题 04 · 消息

Agent 没有嘴

直觉解法

在聊天里说一声；
但会话一重启，上下文就没了。

设计

把消息做成 git 空提交：
可审计、可离线、可重放。

[msg] contract-change user-api -> pcB-ba-1
id: a1b2c3d4
from: pcA-ba-1
to: [pcB-ba-1]
---
POST /login 增加可选 mfaToken
消息不是“说过”，是“留下了一个对象”。

问题 05 · 归属

消息发出去，
谁负责读？

01 本地 inbox

先落盘；同机立即可读。

02 bus

跨机审计与兜底。

03 MQTT

问题 06 · 并发

都在忙，
但没人知道做到哪

  • 01
    队列：需求先入队，不靠“谁先看到”。
  • 02
    认领：原子 claim，WIP=1；一个人只持一个需求。
  • 03
    状态：只有 BA 能改；状态机不是注释。
  • 04

一个需求，一个容器；一个事实，一个写者。

问题 08 · 上下文

上下文不是记忆，
是工作台

稳定事实

项目地图

架构、命令、约定、坑；放 base / 文档，按需引用。

任务状态

当前切片

目标、AC、evidence、待验证；放任务卡 / handoff。

工具输出

临时材料

只留摘要和 path:line；不要把全量日志塞回去。

污染：旧文件 / 旧结论 / 兄弟任务 / 全量日志约束：只放现在要动手的东西
工作台只放“现在要动手”的东西；仓库和历史留在磁盘上。
问题 09 · 重复

BA 摸一遍，
子 Agent 再摸一遍

BA

业务 / 验收 / 文档

不深读实现；需要实现理解就交给 Explore/Dev。

Explore / Dev

代码探索唯一 owner

产出 path:line、命令、假设、待验证；下一个人消费 evidence。

Evidence 最小字段

base_sha · confirmed · commands · unknowns · files_read · do_not_reread

一个任务，一个探索 owner；没有 fork，evidence 就是桥。
问题 10 · 失控

任务太大，
子 Agent 一直跑

症状

读很多文件、多次 compaction、始终没有 diff；
不是任务难，是任务没拆。

设计

BA 做任务预检和切片；
子 Agent 只做 3–5 分钟开工自检，第一次 compaction 就停。

错误：让它再跑一会正确：回 BA 重拆 / handoff
拆分权在 BA，执行可行性判断权在子 Agent。
问题 11 · 换班

常驻 BA 一换，
消息和 claim 就丢

状态按什么隔离换 session 后
inbox / 已读agent_id保留
claim / WIPagent_id保留
session / wakesession_id换租约
agent_id 是工位，session 是租约；
换班不是重启，是 handoff → resume。
设计：handoff 保留 claim / 未读 / 下一步
现在 · 闭环

现在这套东西，
长这样

  • 01
    需求：Planner 定顺序，BA 写验收。
  • 02
    认领：claim next，WIP=1，生成 worktree。
  • 03
    执行：Dev 在 worktree 里改；Explore 只读探索。
  • 04
    验证：QA 按 AC 和 diff 验证；不重新探索架构。
  • 05
    合并 / 回收：contract check → merge → release claim。
不是“更聪明的 Agent”，是“更少的共享状态、更清楚的边界”。
现在 · 代价

这套东西不是免费的

仪式成本

claim、status、contract、handoff；小任务会觉得重。

磁盘 / IDE

每个 feature 一个 worktree；大仓索引压力大。

消息噪音

bus 是审计，不是聊天室；发多了会淹没重要变更。

学习曲线

角色、分支、门禁都要理解；不是装个插件就会。

适用边界：3–8 个 BA、模块相对独立、契约稳定；
否则先不要上全套。

收束 · 三句话

如果只带走三句话

01

先修物理结构，再修协作

共享目录、共享事实、共享身份，最后都会变成事故。

02

先唯一写者，再谈自治

状态、契约、claim 都要有唯一写者；否则越自治越乱。

03

先测结构，再谈单价

成本 ≈ 轮数 × 上下文；先砍重复，再换模型。

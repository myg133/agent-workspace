当一个 Agent
不够用之后

agent-workspace 的由来，
以及几次被问题推着走的转向。
一次技术分享 约 40 分钟 v1.53
起点 · 背景

先从一个很具体的项目说起

多仓库、多模块、需求并行；最多的时候，8 个需求负责人（后来叫 BA）同时开工。

工作台

三个地方

代码、需求、部署分散在不同仓库和分支。

协作

聊天 + 人工搬运

任务靠说，状态靠记，交接靠复制。

结果

能跑，但一并行就乱

冲突、丢消息、状态漂移，开始同时出现。

我们不是先有架构，再找场景；是先被场景逼到墙角。
先对齐 · 它是什么

agent-workspace
到底是什么？

它不是平台，也不是 Agent 框架；它是一套用 Git 承载协作的 skill。

约定

目录、分支、角色

把“谁在哪、做什么”变成可执行的约定。

工具

claim、bus、doctor

把约定变成命令，而不是靠记忆。

门禁

verify、contract

把“应该”变成“过不去”。

它不解决模型聪不聪明，它解决多个 Agent 怎么不互相踩。
第一章 · 单 Agent

最开始，
我们只有一个 Agent

一个 checkout、一个任务、一个人盯着；慢，但不会乱。

需求少

一次只做一件事，顺序天然正确。

串行

没有并发，就没有抢占和覆盖。

人工搬运

上下文、状态、结果，靠人接。

一个 Agent 的时候，所有问题都不存在；
问题是需求不会停在“一个”。
第二章 · 空间

加到第三个 Agent，
它们开始互相覆盖

现场

Agent A 在改登录，Agent B 在改支付；
它们共享同一个 checkout。

直觉解法

“让它们小心一点”“改之前先看一眼”。
结果：仍然冲突，只是更晚发现。

不是模型不听话，是它们共享了同一个“事实源”。
那它们应该站在哪里？
第二章 · 空间

那就先让它们
各站各的地方

repo/
├── main
└── .worktrees/
    ├── REQ-101/
    └── REQ-102/
01 隔离

每个 REQ 一个工作区，互不覆盖。

02 回收

合并即回收；worktree 是容器，不是永久分支。

站的地方分开了，但新的问题不是代码，
而是：谁代表事实？
第二章 · 空间

工作区多了，
谁代表事实？

如果按人分

每个人一条分支、一个目录；
工位变成了事实，合并时没有共同根。

我们最后按事实分

code/ 产品代码
BA/ 需求与状态
Deploy/ 发布与回滚

目录是事实边界，分支是事实的生命周期；
worktree 只是它们的临时视图。
如果是你，会按人分，还是按事实分？
第三章 · 角色

有了地方，
为什么还需要多个 Agent？

不是为了“更多”，是为了三个隔离。

任务并行

独立的需求

互不阻塞，各自推进。

上下文隔离

不同的工作集

避免一个会话背所有模块。

角色边界

不同的写权限

需求、代码、验证分开。

多 Agent 是组织设计，不是并发数；
每多一个 Agent，就多一份协调成本。
如果是你，会先加 Agent，还是先加边界？
第三章 · 角色

早期没有 Planner，
我们怎么活？

1–3 个 BA

本地决策就够：
谁先做、怎么做，BA 自己拍板。

8 个 BA

优先级冲突、跨 BA 契约、
不可逆变更开始互相踩。

Planner 做

顺序、边界、跨 BA 冲突、不可逆决策。

Planner 不做

字段名、实现细节、单个 REQ 的技术选型。

替代方案

BA 投票 / 轮值 lead / FIFO；
各有代价。

Planner 不是老板，是调度器。
3 个 BA 时，你需要 Planner 吗？
第三章 · 角色

谁对需求负责？

Dev 兼需求

实现者定义验收；
容易把“能做”当成“该做”。

PM 兼需求

离代码太远；
边界和验收落不了地。

BA

需求的唯一写者；
验收的定义者；
状态的唯一写者。

BA 不是传话筒，是验收的定义者。
如果让 Tech Lead 兼 BA，会怎样？
第四章 · 消息

他们怎么说话？

聊天、Issue、数据库、Git：为什么最后选了 Git 空提交？

方案优点问题
聊天最快重启即失忆，不可审计
Issue / DB结构化管理与代码分离，跨机同步另做
Git bus可审计、可离线、可重放延迟、噪音、无加密
消息不是聊天，是协作日志。
如果重来，你会用事件总线还是 Git？
第四章 · 消息

消息发出去了，
谁负责读？

bus 单独用

每次 fetch 才能看到；
实时性差，读状态难。

local inbox

先落盘；同机立即可读；
已读/ack 有归属。

MQTT

实时唤醒；
断线自动退回 bus。

bus 是审计，不是唯一路径；
实时和可审计，可以都要。
你会把“消息”和“审计”分开吗？
第五章 · 并发

都在忙，
怎么知道谁在做什么？

不做会怎样

重复做同一个需求；
抢同一批文件；
状态各说各话。

做了之后

queue → claim → WIP=1 → status；
一个需求一个容器，一个事实一个写者。

WIP=1 不是保守，是给并行设一个可解释的上限。
如果吞吐不够，你会加 WIP 还是加人？
第六章 · 成本

协作顺了，
账单开始说话

当我们终于不吵了，才发现钱花得比想象中快。

主会话

prompt / 轮
成本 ≈ 请求数 × 每轮上下文 × 单价；
输出通常最少，真正的大头是“每轮都重新带上的东西”。
如果只能改一个，你会先改轮数还是单价？

那先算一笔账

先问“轮数能不能减半”，再问“单价能不能减半”。
第六章 · 成本

上下文到底该装什么？

稳定事实

项目地图

架构、命令、约定、坑；放 base / 文档，按需引用。

任务状态

当前切片

目标、AC、evidence、待验证；放任务卡 / handoff。

工具输出

临时材料

只留摘要和 path:line；不要把全量日志塞回去。

上下文不是记忆，是工作台；
只放“现在要动手”的东西。
你的会话里，哪一类东西最多？
第六章 · 成本

任务太大，
子 Agent 为什么停不下来？

症状

读很多文件、多次 compaction、始终没有 diff；
不是任务难，是任务没拆。

我们后来怎么做

BA 做任务预检和切片；
子 Agent 只做开工自检，第一次 compaction 就停。

拆分权在 BA，执行可行性判断权在子 Agent。
你会让子 Agent 自己拆任务吗？
第六章 · 成本

常驻 BA 换班，
消息和 claim 怎么办？

状态按什么隔离换 session 后
inbox / 已读agent_id保留
claim / WIPagent_id保留
session / wakesession_id换租约
agent_id 是工位，session 是租约；
换班不是重启，是 handoff → resume。
如果会话必须换，你最怕丢什么？
第七章 · 边界

那要不要干脆
做个平台？

现场自查 · 勾选命中项
0/4

一条都没命中：先用 Skill。

命中两条，再谈平台；平台不是“更高级的 Skill”，是另一类产品。

现阶段 90% 的收益来自“约定 + 门禁”，平台只多给 10%，却要背 100% 的运维。
现在 · 闭环

现在，它长这样

  • 01
    需求：Planner 定顺序，BA 写验收。
  • 02
    认领：claim next，WIP=1，生成 worktree。
  • 03
    执行：Dev 在 worktree 里改；Explore 只读探索。
  • 04
    验证：QA 按 AC 和 diff 验证；不重新探索架构。
  • 05
    合并 / 回收：contract check → merge → release claim。
不是“更聪明的 Agent”，是“更少的共享状态、更清楚的边界”。
复盘 · 如果重来

如果重来一次，
我会保留哪些判断？

  • 01
    先物理隔离，再谈协作：工作区/分支先分清楚。
  • 02
    先唯一写者，再谈自治：状态、契约、claim 都要有 owner。
  • 03
    先可审计，再实时：消息先能留下，再谈秒回。
  • 04
    先测结构，再谈单价：成本 ≈ 轮数 × 上下文。
  • 05
    先最小闭环，再平台：约定 + 门禁跑通，再谈产品化。
这套东西不是免费的：仪式、磁盘、消息噪音、学习曲线，都是代价。
